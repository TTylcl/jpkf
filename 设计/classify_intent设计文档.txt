================================================================================
  意图分类节点 —— 设计文档
================================================================================

  定位：Agent Router 的决策中枢。读用户消息 → 输出 intent + day_of_week，
        决定请求去排课子图、RAG 子图还是通用对话子图。


一、为什么放弃关键词预筛选？

  关键词系统的本质是用形式匹配替代语义理解。看几个真实场景：

  ┌────────────────────────┬───────────────────────┬──────────────────────────┐
  │        用户输入         │       关键词系统       │          LLM             │
  ├────────────────────────┼───────────────────────┼──────────────────────────┤
  │ "我娃今天有啥安排"      │ × 没有匹配模式，漏判   │ √ "安排"+"今天"→ 排课     │
  ├────────────────────────┼───────────────────────┼──────────────────────────┤
  │ "今天学钢琴的时间"      │ × 没有匹配模式         │ √ "时间"+"今天"→ 排课     │
  ├────────────────────────┼───────────────────────┼──────────────────────────┤
  │ "下午有课没"            │ × "有课"触发但缺时间词  │ √ 时间锚点明确 → 排课     │
  ├────────────────────────┼───────────────────────┼──────────────────────────┤
  │ "给我看看课"            │ × "课"太宽泛被忽略     │ √ 结合上下文判断          │
  ├────────────────────────┼───────────────────────┼──────────────────────────┤
  │ "最近在学什么"          │ × 没有模式匹配         │ √ 无时间锚点 → 课程查询   │
  └────────────────────────┴───────────────────────┴──────────────────────────┘

  每多写一条规则，就多一个被绕过的机会。关键词命中率在真实场景中不足 50%。
  用 100% 的 LLM 分类覆盖率换 50% 的关键词性能优化，这笔账不划算。


二、准确率提升的四个维度

  维度 1 + 2 为当前实现（v1），维度 3 + 4 为后续可扩展内容。

  ┌────────┬──────────────────┬──────────┬─────────────────────────────────┐
  │  维度  │      名称        │   状态   │            解决的问题            │
  ├────────┼──────────────────┼──────────┼─────────────────────────────────┤
  │   1    │ 对话历史压缩注入  │ ✅ 已实现 │ 消除指代歧义（"那明天呢"）      │
  ├────────┼──────────────────┼──────────┼─────────────────────────────────┤
  │   2    │ 用户画像注入      │ ✅ 已实现 │ 消除身份歧义（parent vs student）│
  ├────────┼──────────────────┼──────────┼─────────────────────────────────┤
  │   3    │ 边界样本 + 思维链 │ 📋 可扩展│ 消除模糊歧义（"今天学什么"      │
  │        │                  │          │ vs "在学什么"）                  │
  ├────────┼──────────────────┼──────────┼─────────────────────────────────┤
  │   4    │ 置信度 + 降级     │ 📋 可扩展│ 不确定时不硬猜，走 general 兜底  │
  └────────┴──────────────────┴──────────┴─────────────────────────────────┘


三、维度 1：对话历史压缩注入（✅ v1 已实现）

  问题：用户说"那明天呢"，分类 LLM 只看到这一句，不知道上一轮在聊什么。

  方案：从 state["messages"] 取最近 3 轮对话，压缩为摘要文本，和当前消息
        一起注入到 HumanMessage。

  设计决策：
  - 取 3 轮，不是全量 —— 太长的历史会稀释当前消息的权重
  - 跳 ToolMessage —— 工具返回的 JSON 数据对意图分类无意义
  - AIMessage 只要文本，跳过纯 tool_calls（无 content 的 AIMessage）
  - 字符上限 500，从旧到新截断

  效果示例：
    原始消息："那明天呢"
    注入后：
      【对话历史】
      用户：小明今天有课吗
      系统：小明今天周二有钢琴课，下午3:00-4:00
      【当前消息】
      那明天呢

    LLM 推理：上一轮在聊小明的排课 + "明天"是时间锚点 → parent_schedule


四、维度 2：用户画像注入（✅ v1 已实现）

  问题："最近学什么"—— parent 说这句话意思是"我孩子在学什么"，
        student 说这句话意思是"我在学什么"。分类 LLM 需要知道调用者身份。

  方案：从 state 已有字段构造用户画像文本，注入到 SystemMessage。

  画像内容：
  - 用户角色（parent / student / teacher / admin）
  - 关联孩子列表（从 state.children_data 读取，不存在则标注"未获取"）

  设计决策：
  - 不主动查数据库 —— classify_intent_node 的职责是分类，不应有副作用
  - children_data 不存在时写"未获取"而不是触发查询
  - 查孩子是排课子图里 get_my_children 工具的事，职责归属更清晰


五、维度 3：边界样本 + 思维链（📋 后续可扩展）

  问题：最难分的是边界 case。"今天学什么"——
        有"今天"（时间锚点 → 排课）但问"学什么"（内容 → 课程）。

  方案：在 prompt 中给出边界样本作为类比参照，同时要求 LLM
        先写一行推理再输出 JSON。

  当前暂不实施原因：
  - GPT-4o 不支持 with_structured_output 同时保留推理 token
  - 需要走"自由输出 → 正则提取 JSON"路线（方案 A）
  - 正则提取的容错性和稳定性需要验证

  实施条件：
  - 维度 1+2 上线后，收集 200 条真实分类日志
  - 标记误分类的边界 case
  - 补充进 prompt 的边界样本表
  - 引入"推理："行 + 正则提取 JSON


六、维度 4：置信度 + 降级策略（📋 后续可扩展）

  问题：LLM 总会遇到拿不准的情况。此时最坏选择是"硬猜一个"。

  方案：LLM 输出 confidence 字段，低于阈值（如 0.85）自动降级为 general。

  当前暂不实施原因：
  - LLM 自我校准能力不稳定，置信度数值不可靠
  - 需要先收集真实数据，分析"误分类时的置信度分布"后再定阈值
  - 过早引入 confidence 字段会增加输出复杂度，可能降低意图判断本身的质量

  实施条件：
  - 维度 1+2 线上稳定运行至少一周
  - 收集误分类样本，人工标注后画出"阈值 vs 误路由率"曲线
  - 选择一个使误路由率 < 5% 的阈值


七、技术路线：为什么不用 with_structured_output

  LangChain 的 with_structured_output 底层调 OpenAI 的 response_format。
  在 GPT-4o 上这个特性工作良好，但有两个限制：

  1. 推理链缺失：with_structured_output 让模型直接输出 JSON token，
     不会产生推理文本。推理过程虽然最终被丢弃，但生成它的过程激活了
     更多语义权重，让分类更准。

  2. 代理兼容：当前走 base_url 代理，response_format 参数可能被
     代理层丢弃或改写。纯文本输出 + 正则提取 JSON 不依赖此特性。

  v1 暂时保留 with_structured_output（维度 3 未启用时推理链收益有限），
  维度 3 启用时切换为自由输出 + 正则提取。


八、非 parent 角色短路

  三个子图中，排课查询和课程 RAG 都是为 parent 设计的。
  student / teacher / admin 的所有需求都能被通用 ReAct 子图覆盖。

  所以非 parent 角色不调分类 LLM，直接返回 general。
  这是业务短路，不是技术限制 —— 省一次 LLM 调用。


九、LLM 调用失败时的降级策略

  意图分类是路由优化，不是功能必须：

  - 分类成功 → 走最优子图（快）
  - 分类失败 → 走通用 ReAct 子图（也能正确回答，只是慢一点）

  所以异常或解析失败时静默降级为 general，不抛异常中断请求。


十、AgentState 字段约定

  分类节点写入的字段（需在 agent/state.py 中定义）：

  ┌─────────────┬──────────────┬──────────┬──────────────────────────────┐
  │    字段     │    类型      │  必填    │            说明              │
  ├─────────────┼──────────────┼──────────┼──────────────────────────────┤
  │ intent      │ str          │ 是       │ parent_schedule /            │
  │             │              │          │ parent_course / general      │
  ├─────────────┼──────────────┼──────────┼──────────────────────────────┤
  │ day_of_week │ int \| None  │ 否       │ 1-7（1=周一..7=周日），      │
  │             │              │          │ 未指定则为 null              │
  ├─────────────┼──────────────┼──────────┼──────────────────────────────┤
  │ confidence  │ float        │ 否       │ 分类置信度 0.0-1.0           │
  │             │              │          │ （v1 预留字段，暂不参与路由） │
  └─────────────┴──────────────┴──────────┴──────────────────────────────┘
