---
  设计理念说明

  1. 为什么权限校验放在最前面？

  请求进来 → 权限校验 → 意图分类 → 路由 → 子图执行
                ↑
           这里拦截

  每往下一层，成本都在增加。意图分类要走 LLM，三个子图也要走 LLM +
  工具调用。如果一个非法请求在前面就能拦截，后面所有成本都是零。这对 API
  计费和响应延迟都有实际意义。

  2. 为什么不做成装饰器，而是独立节点？

  项目中已有 @tool 装饰器和 AGENT_PERMISSIONS_MATRIX
  做工具级权限控制。但那是细粒度的 —— 判断"这个角色的用户能不能调这个具体工具"。

  本节点做的是粗粒度的 —— 判断"这个人能不能用这个系统"。

  两层互补，不是替代：

  ┌──────────────────┬──────────┬────────┬──────────────────────────────────────┐
  │       层级       │   位置   │  粒度  │               拦截什么               │
  ├──────────────────┼──────────┼────────┼──────────────────────────────────────┤
  │ 第一层（本节点） │ 图入口   │ 角色级 │ 未登录、角色不存在、user_id=0        │
  ├──────────────────┼──────────┼────────┼──────────────────────────────────────┤
  │ 第二层（已有）   │ ToolNode │ 操作级 │ customer_service_agent 试图          │
  │                  │          │        │ delete_schedule                      │
  └──────────────────┴──────────┴────────┴──────────────────────────────────────┘

  3. 为什么通过时返回 {} 而不是原样返回 state？

  LangGraph 的节点返回是增量合并（reducer），不是替换。返回 {} 意味着"state
  没有任何字段需要更新"，state 原样往下传。这是 LangGraph 的惯用写法。

  拒绝时返回 {"messages": [...], "permission_denied": True} —— 新增一条 AIMessage
  追加到消息历史，同时设置 permission_denied 标记。后续的条件边读这个标记直接跳到
  END，不再进入意图分类。

  4. 为什么用 frozenset 而不是 list？

  白名单是常量集合，不会被修改。frozenset 明确表达了这个语义，且 in 查找是
  O(1)。这里数据量很小，性能差异可忽略，但它是一份文档——
  告诉阅读代码的人："这个集合永远不会变"。

  5. AgentContext 和 CTX 的区别

  这里用的是 AgentContext（Runtime 上下文），不是 CTX（Service 上下文）：

  - AgentContext：来自 config.configurable，由 API 层注入，只含 user_id /
  agent_role / user_role / trace_id / wx_openid
  五个字段。它在图的整个生命周期都可访问。
  - CTX：在 Service 层创建，需要 session（数据库连接），frozen=True 不可篡改。它在
  ToolNode 执行工具时才被组装。

  权限校验只需身份字段，不需要数据库连接，所以用 AgentContext 就够了。

  6. 为什么把 user_id 的校验放在最后？

  这是刻意为之。前两个校验（user_role、agent_role）失败时，错误消息更具体，能让用户
  /开发者更快定位问题。user_id 校验放在最后是因为：

  - user_role 和 agent_role 是配置问题（配错了就是配错了），需要立刻暴露
